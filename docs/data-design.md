# 数据模型草案

状态：设计基线；核心测试版已实现首版数据契约，详见[开发说明](development.md)。记录日期：2026-11-05；更新日期：2026-11-23。任务与术语界面仍待实现。

本草案落实[需求约定](requirements.md)中的多语言、左右对照、术语注释和性能要求。术语注释界面可以后续实现，但相关信息需要从首次构建词库时保留。

## 1. 需要支持的查询

- 已知实体类型和 ID，查询指定语言的名称。
- 已知任务 ID 和字段，取得原文、译文及可用的对齐信息。
- 已知正文，取得其中已经确认的术语引用，按用户设置追加译注。
- 没有预先标注的文本，通过源语言术语索引匹配候选词，再依据上下文决定是否注释。

不能把这些查询全部简化为英文字符串到中文字符串的映射。同一个词可能指向多个实体；相同数字 ID 在不同实体类型或游戏版本下也不能默认代表同一条内容。

## 2. 实体、术语和文本分开存储

### 实体记录

首版只有 Forever 的一套当前词库，游戏分支放在包级元数据中，实体以类型和 ID 定位。适用客户端范围及来源构建单独记录，不为每个历史版本复制记录，也不做跨版本查询路由。

各语言名称保存在同一实体的本地化记录中，保留源语言名称。拥有中文名称但没有英文名称的数据仍可按 ID 使用，但不能声称支持英文正文中的名称匹配。

### 术语记录

术语具有稳定的内部键，可以关联游戏实体，但不要求存在游戏 ID。地点、组织、概念和通用游戏术语都可能需要自己的术语记录。

建议记录：

| 字段 | 用途 |
| --- | --- |
| 术语键 | 与语言无关的内部标识 |
| 类别 | 地点、人物、物品、技能、组织、概念等 |
| 实体关联 | 可选的游戏分支、类型和 ID 引用 |
| 各语言名称 | 展示名称与默认简短译注 |
| 各语言别名 | 完整短语、缩写及经确认的词形 |
| 匹配规则 | 大小写、边界、允许的上下文和歧义处理 |
| 来源引用 | 指向来源清单，记录原插件或数据来源及其版本；首版不要求每条术语拥有独立修订号 |

一个英文词形允许对应多个候选术语，不能用简单字典覆盖掉同名项。有歧义且缺少上下文时保持原文。

### 文本记录

任务等长文本按实体、字段和语言保存正文，例如标题、目标、描述、进行中与完成对白。除正文外，可包含两类独立标注：

1. 对齐关系：哪些源语言片段对应哪些目标语言片段，允许一句对多句或多个句子组成一组。
2. 术语引用：哪个源文本片段对应哪个术语，避免游戏运行时再次猜测。

同一条正文供不同显示策略读取，不分别维护整段中文版、双语版和带括号注释版。无译文、无对齐信息、无术语标注是不同状态，不能合并成一个“缺失”。

## 2.1 首版采用单一当前数据集

首版只保留一套当前词库，更新时替换该数据集，不实现历史版本并存、按客户端构建自动选择词库或数据版本切换 UI。源码与数据历史由 Git 保存。

建议的最小包级元数据：

- `schemaVersion`：数据格式版本，用于判断加载器是否支持该格式。
- `dataRevision`：整包数据修订标识，用于缓存和索引失效；不意味着同时分发多个版本。
- `game` 与目标客户端范围：限定数据所属游戏及适用环境，验证状态与单纯版本匹配分开表达。
- `sources`：所参考或导入的插件、具体版本、来源链接和许可信息；不同来源可以用短键引用。

正文指纹用于确认预标注仍匹配当前文本，不是另一套历史版本库。缺译、歧义、未核对或缺少对齐等质量状态与版本管理独立，保留一个数据集也仍需区分这些情况。

## 3. 示例：一份文本支持两种显示

下面是说明结构的示例，不代表已导入的游戏文本或既定序列化格式：

```text
术语键：place.stormwind
  enUS 名称：Stormwind
  zhCN 名称：暴风城

英文正文片段：
  text("Travel to ")
  term("place.stormwind", original="Stormwind")
  text(".")

对应中文片段：
  text("前往暴风城。")
```

完整对照显示时读取两侧对应片段；术语注释显示时保留英文片段，并在术语片段后插入目标语言短译注。只展示名称时直接使用实体或术语名称记录。

这是逻辑表示，最终运行包不一定为每个片段创建 Lua 小表。源码格式和运行时编码分别设计并通过测量选取。

## 4. 标注与变量的正确性

- 标注应绑定正文修订或内容指纹；正文变化后，旧位置标注必须重新验证。
- 不能依赖渲染后的屏幕行号；字号和换行会改变行布局。
- 如果采用范围标注，生成器和运行时必须约定坐标单位，避免把 UTF-8 字节偏移与字符序号混用。
- 玩家姓名、数量、职业等动态参数以独立占位符或等价结构表达；展开变量不能使后续术语位置失效。
- 超链接载荷、颜色和纹理标记与普通可注释文本区分处理，避免破坏游戏标记。
- 源文本与词库版本不匹配时，不使用失效的预标注；保留原文或使用已经验证的回退路径。

## 5. 构建与运行时的分工

准备数据时执行术语整理、候选匹配、歧义校验、句组对齐与索引生成。对固定正文，优先产出可直接使用的术语引用。

游戏内尽量只执行 ID 查找、引用读取、变量展开、样式处理和绘制。只有缺少预标注的支持文本才进行词语匹配；首版不为未来聊天自由文本预建通信或模型功能。

初始技术提案采用 UTF-8 JSON 保存可审阅源数据，由 Python 工具校验并生成 Lua 数据表与索引，详见[开发规划的技术基线](implementation-plan.md#2-技术基线与工程组织)。具体字段及运行表布局在样例阶段确定，首版不预设压缩编码。运行包按功能组织，不要求加载所有任务正文才能显示一个物品名称。缓存和索引包含相关数据修订，数据更新后不会沿用错误匹配。

为便于性能评估，区分按 ID 查询、预标注渲染和现场文本匹配三条路径，分别测量成本。

## 6. 用户偏好不写入公共词库

已熟悉术语的忽略列表、用户译文覆盖、注释颜色和重复注释策略属于账号设置。它们引用稳定术语键，更新语言包时不应丢失。

基础词库保留原始内容和来源，不因用户关闭某类注释而删除记录。个人忽略列表等交互仍是待确认的具体功能，不影响先建立上述数据边界。

## 6.1 数据来源与提取

方向（2026-11-24）：数据源是翻译质量的核心，优先自行提取，不以复用社区插件的数据作为主要来源。以下依据 2026-11-24 的调研，部分前提仍需验证。

### 两类数据

| 类别 | 内容 | 获取方式 |
| --- | --- | --- |
| 客户端数据表（DB2） | 物品名称与风味文字（ItemSparse）、技能名称（SpellName）、技能说明（Spell）、区域（AreaTable）、阵营（Faction）、套装（ItemSet）、物件（GameObjects） | 同一构建号分别导出 enUS 与 zhCN，按 ID 合并。wago.tools 提供 Forever（产品名 `wowf`）各构建的按语言 CSV；备选是用 CASC 工具从客户端文件直接提取 |
| 服务器下发的文本 | 任务标题、目标、正文、进度与完成对话；NPC 名称与头衔；NPC 对话 | 客户端数据表中没有（Forever 的 Creature 表只有 189 行，QuestV2 不含文本，BroadcastText 只有 13 行）。只有在客户端向服务器查询后，按客户端的文本语言下发，并写入本地缓存（WDB） |

解包客户端（CASC）得到的就是这些数据表，wago.tools 也是用同样的方式从暴雪 CDN 提取的。CDN 上保存着所有语言的数据表，因此英文客户端也能解包出中文表。按 WoWDBDefs 收录的全部表名查找，任何版本都没有存放任务正文的表；Forever 中与任务、对话相关的表（QuestV2、GossipNPCOption、ConversationLine 等）只有 ID 和引用，没有中文文本。所以解包可以替代 wago.tools，但拿不到服务器下发的文本。

实测 `1.60.1.71037`：ItemSparse 有 17,495 条中文物品名，SpellName 有 27,204 条中文技能名，Spell 有 17,274 条中文说明，其中 12,873 条含 `$s1`、`$d` 等变量模板。技能说明的变量换算属于 P5 的工作，与数据来源无关。

### 服务器文本的自行采集

Battle.net 的版本服务显示 Forever 在 us、eu、cn、kr、tw 五个区域发布同一构建，cn 区域使用网易的 CDN。因此简体中文的服务器文本可以通过国服 Forever 客户端获得；tw 区域是繁体中文，用词与简体版本不同，不能直接替代。

采集方式：

- **任务标题、目标与正文**：采集插件按任务 ID 列表（客户端 QuestV2 表约 6,600 个 ID）向服务器发起查询，服务器返回的内容写入客户端的任务缓存文件，离线工具再解析缓存文件。
- **NPC 名称与头衔**：通过生物超链接触发查询，写入生物缓存。NPC ID 列表需要另找来源。
- **进度与完成对话、NPC 对话**：只有与 NPC 实际交互才会下发，需要长期在游戏中积累，或由自愿的玩家使用采集插件提供。
- **英文原文**：在 us 或 eu 的英文客户端上用同样的方法采集，作为逐句对照的英文源。

前提与风险：

- 需要国服账号与游戏时间。先确认 eu 或 us 客户端的文本语言能否选择简体中文；如果可以，就不需要国服账号。
- 批量查询需要限速，避免对服务器造成异常负载；需评估是否违反服务条款。
- 缓存文件格式可能随构建变化，解析工具要按构建号校验。

工作量估计：客户端数据表的导出与合并约 1–2 天，之后每次更新只需重跑；采集插件和缓存解析工具约 1–2 周；每次版本更新后的批量采集需要数小时游戏内时间；进度、完成与对话文本需要长期积累。

## 6.2 任务与 NPC 文本的来源调研

记录日期：2026-11-24。结论尚未决定，任务文本翻译因此暂缓。

- **现有中文插件的做法**：WoWeuCN 系列使用暴雪官方的简体中文文本，而不是自行翻译。经典旧世部分来自网络流传的国服文本；Forever 部分由作者用国服账号自费扫描；WoWeuCN Plus 另外使用了一份 Forever 的 zhCN 任务缓存、QuestEcho 社区数据，以及 QuestieDB 从 Wowhead 抓取的标题和目标。
- **MaNGOS Zero 本地化包**（`mangoszero/database` 仓库的 `Translations`，GPLv2）：包含 4,248 个任务的中文（标题 4,198、正文 3,676、目标 3,635、完成对话 4,079、进度对话 3,118），以及 NPC 名称、NPC 对话、对话选项、书信、怪物喊话。英文原文在同一数据库中，按 ID 一一对应，并保留 `$N`、`$C`、`$B` 等占位符。它是社区整理的译文，部分标题与官方不同（例如任务 2 为“尖爪的爪子”，官方为“沙普塔隆的爪子”），并混有少量繁体字和台服译名（抽样约 0.3%）。
- **机器翻译**：全部任务文本约 80–100 万英文词，人工翻译不可行；机器翻译在构建阶段完成，按句翻译时对齐关系天然存在，但需要套用官方术语表，并明确标注。
- **建议的分层**：官方中文（客户端数据表；以后的中文客户端采集）优先，其次是人工审校的译文，最后是标注为“机翻”的机器翻译；以 MaNGOS 作为经典旧世任务底本时，Forever 新增和改动的部分（Wowhead 标记约 1,175 个新增、594 个更新）再用机器翻译补足。
- **许可影响**：使用 MaNGOS 衍生内容时，相关数据包须以 GPLv2 发布。GPLv2 不限制修改和扩充，但要求以相同许可分发并提供源码，不能加更严的条款，也不能合并许可不兼容的数据；MaNGOS 是“仅 GPLv2”还是“GPLv2 或更高版本”尚待核实。

## 7. 首批数据与待定事项

首批数据按 6.1 节自行提取：先导出客户端数据表中的物品、技能等名称，验证数据模型和生成流程；任务与 NPC 文本等服务器数据在采集方案确认后再接入。WoWeuCN Plus 和 qqytqqyt 的 WoWeuCN 插件只作为覆盖范围和格式的参考，暂不作为数据来源。

导入时检查各记录是否同时具有英文、中文、明确 ID 和正确字段。缺少英文正文或句级对齐的数据不能直接视为已支持逐句对照；需要补齐源文并建立对应关系。首次导入保留来源清单，运行包只生成当前选定数据集。

仍需决定：

- JSON 源文件的拆分与字段规范，以及生成 Lua 运行表的具体布局。
- 游戏实体类型命名、内部术语键规范和整包修订标识形式。
- 文本片段、占位符及对齐关系的具体字段定义。
- 服务器文本的采集前提：eu／us 客户端能否选择简体中文文本，或是否使用国服账号；批量查询的限速与服务条款评估。
- 术语类别和样例范围。
- 预标注生成与校验工具，以及没有完整双语源数据时的回退规则。

本草案明确需要保留的信息和查询能力，不代表所有词库记录现在必须具有完整句级对齐或术语标注。
