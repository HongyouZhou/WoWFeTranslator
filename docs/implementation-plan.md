# WoWFeTranslator 开发规划

状态：P0／P1 核心测试版已实现，开发环境验证通过；正式词库导入与 Windows 游戏内验收待完成。

日期：2026-11-05；进度更新：2026-11-23。

当前交付：`0.1.0-alpha.1`，13 条手工名称样例、按需数据包、原版物品提示双语卡片、账号设置、界面开关／模式／样式、诊断与可复现 ZIP。安装与实际验收见 [Windows 测试指南](windows-testing.md)，代码和具体数据格式见[开发说明](development.md)。

首轮实现采用较少的顶层 Lua 文件组织模块，后续规模增长再拆目录。任务／术语数据结构用合成样例验证，不代表相关游戏界面已实现。正式参考词库尚未导入；当前使用明确标记的手工工程样例，先完成可安装验证链路。

需求依据：[需求与验收约定](requirements.md)。数据设计依据：[数据模型草案](data-design.md)。本文安排实现顺序、模块边界和交付检查；具体文件名与内部接口为初始方案，可在实现中按实际需要调整。

## 1. 交付目标与边界

先交付可供内部测试的 Windows / WoW: Forever 插件，第一条语言路径为英文到简体中文，仅适配暴雪原版界面。初始客户端参考为 `1.60.1.70790 / Interface 16001`，实际接口需在开发时核实。

基本功能与性能同时交付。首先跑通物品名称的完整流程，随后增加 NPC 与技能名称、任务双栏阅读、术语注释和动态效果说明。最小版本不以词条数量为成功标准，以数据结构、交互行为和运行成本得到验证为成功标准。

首阶段不实现：本地模型、自由聊天翻译、伴随程序、快捷键、自动场景切换、第三方 UI 适配、角色独立配置、多版本词库切换或公开发布自动化。

账号共享设置；开关和模式通过 UI 按钮控制。项目许可证、公开发布安排和具体 Windows 测试环境按用户决定后续讨论，不将这些讨论提前变成开始设计的条件。实际引入第三方内容时仍记录并核对其来源与许可。

## 2. 技术基线与工程组织

### 建议的首版技术选型

以下是开始实现前的技术提案，不代表代码或客户端验证已经完成。先明确运行环境和数据流，再以小样例验证，随后扩展模块。

| 层次 | 首版建议 | 选择理由与边界 |
| --- | --- | --- |
| 游戏内逻辑 | Lua，使用目标客户端支持的语法与 API | 与插件运行环境一致；查询、翻译处理与界面适配分离。具体兼容语法和测试解释器在 P0 核实 |
| 游戏内界面 | 原生 Frame / FontString，由 Lua 创建控件 | 先支持原版 UI 和共享滚动容器；暂不引入第三方 UI 框架，XML 模板有实际需要时再采用 |
| 开发工具 | Python 3，初期优先标准库 | 用于提取、校验、索引生成和打包；仅开发者需要，玩家安装包不依赖 Python |
| 可维护源数据 | UTF-8 JSON，按内容类别及合理大小拆文件 | 便于审阅、多语言编辑和 Git 比较；字段规范与引用校验独立于文件格式 |
| 游戏运行数据 | 构建时生成的 Lua 数据表与预生成索引 | 游戏内直接查询，不在交互时解析 JSON；按功能拆包，验证按需加载后的成本 |
| 用户持久设置 | 账号级 SavedVariables | 保存开关、模式、字体、字号和颜色；与分发词库及临时缓存分离 |
| 临时缓存与诊断 | 有容量限制的内存表 | 不把可重建缓存或逐次诊断记录持续写入账号设置 |

Python 的最低版本与开发依赖在实现工具时记录；Lua 兼容性以实际游戏客户端为准，不直接假定开发机解释器与游戏完全一致。首版无需数据库服务、SQLite 或外部进程依赖；未来聊天模型单独设计。

### 源数据、运行数据与设置分别存储

这里的“翻译数据库”是逻辑词库，不要求引入数据库引擎。数据流为：

`可审阅 JSON → Python 校验／生成 → Lua 数据包 → 游戏内按类型、ID、语言查询`

JSON 是维护入口，生成的 Lua 文件不手工修改。生成器负责字符串转义、稳定输出顺序、引用检查和索引生成；首批运行表以易检查为优先。JSON 中的实体 ID 与生成后的 Lua 索引键必须有明确转换规则，避免字符串键与数字键不一致导致查不到数据。

源文件拆分不等于游戏内按需加载；后者需要独立的数据插件包及加载入口，具体粒度以首次加载与内存测量调整。普通 Lua 文件的分开存放本身不提供按需加载。

账号设置独立保存，并记录设置格式版本以便补齐默认值或迁移。它与词库的 `schemaVersion`、`dataRevision` 职责不同，也不意味着保留多套历史词库。翻译表和可重建缓存不复制进 SavedVariables。

第一轮采用直观的数据编码与 ID 索引。压缩、复杂索引或其他运行库只有在测量表明有收益时再引入；性能核心首先是运行时做多少工作、何时加载、查找范围和对象分配，而非源文件使用哪种格式。

### 工程目录

拟采用以下结构，按阶段增加文件，不预先创建空模块：

```text
addon/
  WoWFeTranslator/
    WoWFeTranslator.toc
    Core/             初始化、账号设置、模式、待执行任务、缓存
    Data/             数据清单和查询入口
    Translation/      变量展开、术语注释、动态文本处理
    Adapters/         原版提示框与任务界面接入
    UI/               按钮、设置、样式、提示呈现、双栏阅读
    Diagnostics/      可关闭的计时和有限统计
  WoWFeTranslator_Data_*/  按功能拆分的运行数据包，随需要增加
data/
  sources/            可审阅数据、来源清单、对齐与术语标注
tools/                导入、校验、生成与内部打包工具
tests/                核心行为、数据一致性和回归样例
benchmarks/           固定负载与测量结果说明
docs/
```

## 3. 模块职责和调用路径

| 模块 | 输入与输出 | 约束 |
| --- | --- | --- |
| Settings / Mode | 个人偏好与当前模式 → 有效功能集合 | 不用切换模式覆盖个人设置 |
| Adapters | 游戏事件和可见内容 → 类型、ID、原文及上下文 | 集中处理游戏 API，检查数据是否可读 |
| Repository | 类型、ID、语言、字段 → 记录及数据状态 | 名称查询不加载整套任务正文 |
| Translation | 记录、原文与参数 → 名称、双语句组或注释片段 | 不依赖具体 Frame，也不决定颜色和字号 |
| Presenters / Style | 内容及显示配置 → 对应界面 | 管理所属控件、排版、刷新与恢复 |
| Scheduler / Cache | 待更新内容与查询键 → 合并任务和复用结果 | 有容量边界、失效机制和取消机制 |
| Diagnostics | 指定处理区间 → 有限样本及统计 | 默认关闭，不把日志写入每次交互路径 |

初始逻辑调用路径：

`事件 → 有效功能检查 → 获取可读上下文 → 查数据／复用缓存 → 必要的翻译处理 → 显示`

名称、任务对照与术语注释共享查询和样式边界，但不强行使用同一套解析算法。数据缺失、无对齐、参数无法解析和接口受限分别返回状态，不用空字符串混淆所有失败情况。

模式预设控制启用哪些能力；左右对照、名称显示和术语注释属于显示策略。最小版本先提供剧情、精简、竞技三个预设，术语模式在相应能力完成后再显示为可用选项。

## 4. 数据准备与生成

### 单一当前词库

运行包只包含当前数据集。保存 `schemaVersion`、`dataRevision`、游戏与客户端范围以及来源清单，不实现历史数据路由。Git 保存修改历史。

源数据从开始就分开表达实体、术语、正文及标注：

- 实体按类型和 ID 定位，保留各语言名称。
- 术语拥有稳定内部键，可关联实体，支持没有游戏 ID 的概念。
- 正文按字段和语言保存，附可选的句组对齐、变量和术语引用。
- 个人偏好独立存储，不将用户样式或忽略列表烘焙进公共词库。

### 首批样例

参考此前研究的 WoWeuCN Plus 与 qqytqqyt 插件，选取明确版本的包，记录出处和许可。初始建议规模为十余条物品名称、少量 NPC／技能名称，以及几条覆盖不同情况的任务；数量不是验收门槛。

先建立代表性样例，再扩大词库。样例需要覆盖多词名称、缺译、同名歧义、变量、长短句、不同句数、链接和显示标记。只有中文的记录不能冒充完整双语记录，缺少英文或对齐关系时明确标记并补齐。

导入流程：

`固定来源包 → 提取字段 → 规范化记录 → 保留来源 → 对齐／标注 → 校验 → 生成 Lua 包`

源包只作为数据输入，不执行其任意初始化代码。固定正文的语义对齐与术语确认在构建阶段完成；第一批少量样例可以人工核对，游戏内不做语义推断。尚未确认的候选标注不能直接当成确定结果。

生成工具检查 ID、术语引用、字段类型、占位符、对齐范围、源文指纹和数据包元数据。相同输入应产生一致的输出；运行包不含原始下载包、开发笔记或用户聊天记录。

## 5. 开关与更新生命周期

初始化时读取账号设置和轻量数据清单，根据有效能力加载必需数据并接入支持的界面。不要为所有界面提前创建完整控件或编译全部模板。

切换开关、模式、语言或影响输出的配置时：

1. 更新有效能力和相关失效标识。
2. 让旧的排队任务失效，阻止它们再次写入旧结果。
3. 清理本插件拥有的显示内容，或按安全条件恢复原文。
4. 对仍需显示的支持界面安排一次合并刷新。

可采用更新代数作为旧任务失效标识，避免逐个追踪所有延迟回调。刷新执行前同时检查代数、当前界面内容和有效能力。

竞技模式和总开关关闭时，钩子只保留必要的判断；不查询词库、不匹配术语、不渲染译文。无法立即完成的受保护界面恢复作为单独待办，在允许的时机处理。关闭不承诺立即卸载所有 Lua 数据。

性能诊断可独立启用来测量关闭状态的成本。正常关闭诊断时，不保留逐次采样或持续日志工作。

## 6. 实施阶段

依赖顺序为 P0 → P1 → P2 → P3 → P4 → P5 → P6。每阶段形成可审查的交付，不在基础链路尚未验证时扩大数据量或界面覆盖。

| 阶段 | 交付物 | 完成条件 |
| --- | --- | --- |
| P0 技术基线、数据契约与样例 | 记录 Lua 兼容要求与工具版本，明确 JSON → Lua 构建流程、设置存储及加载边界；字段规范、来源清单、代表性数据、校验及生成入口 | 小样例能生成可查询的 Lua 数据；能同时表达名称、双语正文和术语引用；重复生成一致，错误引用能被发现；客户端相关假设列出验证状态 |
| P1 物品名称最小版本 | 可加载插件、账号设置、UI 开关和模式、名称左右对照、基本样式、可关闭性能统计、内部安装包 | 同一提示不重复显示，切换物品无残留，关闭后停止处理，旧任务失效；取得首次与重复查询的测量结果 |
| P2 扩展名称覆盖 | NPC、技能名称适配，模块独立开关 | 三类名称复用查询和显示逻辑；关闭一类不影响另一类；增量数据与处理开销有记录 |
| P3 任务双栏阅读 | 任务字段查询、变量展开、句组排版、同步滚动 | 左右句组在滚动、不同字号和宽度下保持对齐；原版接交操作正常；缺字段和切任务正确处理 |
| P4 术语注释 | 预标注渲染、必要的候选匹配、术语模式入口和注释样式 | 原句保留，短语和边界正确；歧义回退；不破坏链接和变量，不重复注释；性能与词库规模有测量 |
| P5 详细效果 | 物品风味文字、技能和装备效果模板、当前数值映射 | 成功匹配时使用当前值，失败保留原文；精简和竞技模式不进入详细解析路径 |
| P6 内部测试收敛 | 扩充已核对词库、内部 ZIP、使用说明、回归与性能报告 | 在已安排的 Windows 客户端完成核心场景验证，记录已知限制和覆盖范围 |

P0 定义并验证术语数据结构，P4 才接入完整注释界面；不能因 P4 较晚而先设计成仅有中文名称的临时数据库。

P1 中剧情与精简模式的显示可以暂时相同，因为只支持名称，但必须保留独立状态和后续能力边界。未完成的功能不以可用按钮误导测试者。

### P3 的排版方案

在原版任务界面旁提供可关闭的双栏阅读面板。一个滚动区域承载两列；每个对应句组共享一行，行高取两侧文字高度的较大值。鼠标在任一列上滚动都改变同一垂直偏移。

字号、宽度或内容变化时重新布局，普通滚动只改变滚动位置，不重复翻译或测量全部文字。长文控件是否需要复用或可见区渲染由实际测量决定，不在原型阶段预设复杂虚拟列表。

测试应覆盖窗口底部、左右文本长短差异、缺少单侧译文、切换任务和隐藏面板。没有可靠句级对齐的记录采用明确的段落对照，不能伪造一一对应。

### P4 的注释方案

优先读取构建阶段的术语引用。对没有预标注且属于支持范围的文本，使用按需匹配索引，不逐条扫描全词库。以原始文本作为输入，避免对已经注释的输出再次注释。

首次出现才注释和用户忽略列表仍为待确认选项；数据和缓存边界允许扩展，但不把这些交互作为 P1 的前置条件。混排中的独立字体与字号先验证实际控件能力，必要时使用片段布局。

## 7. 性能实现与测量

先采用尽早返回、按需加载、ID 查询和合并更新等简单措施。每项额外优化要有固定负载下的前后对比，并同时验证结果正确。

### 三条路径分别测量

| 路径 | 关注点 |
| --- | --- |
| 按 ID 查询名称 | 首次加载、重复查询、提示框刷新和内存增量 |
| 已标注正文渲染 | 变量展开、句组和注释排版、滚动时是否重复处理 |
| 现场文本匹配 | 模板或术语候选数量、缓存命中、长文本与歧义输入 |

缓存条目有容量边界。查询缓存与显示布局缓存按依赖分别失效，避免改颜色就重新解析数据，也避免技能数值变化后仍显示旧译文。失效因素包括数据修订、语言、原文或动态上下文、模式，以及相关样式／偏好修订。

诊断初期使用有界样本，记录调用次数、累计及平均耗时、最大耗时、缓存命中和内存变化；P95 在报告生成时根据保留样本计算，注明样本窗口，不在每次事件中排序。测量工具本身的开销要单独说明。

区分插件处理耗时、数据加载耗时和整体游戏帧表现。P1 取得第一份可用基线后再设定数值预算，不预先宣称任何毫秒或内存目标已经满足。

## 8. 验证安排

### 开发环境

围绕容易回归的行为做测试：数据引用和生成一致性、缺译回退、占位符展开、缓存失效、关闭后的旧任务、术语边界和标记保护。测试断言行为，不照抄实现。

通过少量游戏接口替身隔离纯逻辑测试，明确其不能验证实际受保护状态、字体测量和 Frame 生命周期。Lua 语法检查与核心逻辑测试使用与目标客户端相容的环境。

### Windows 游戏内

具体硬件、安装目录和测试协作按用户要求稍后安排。每个里程碑分别标记“开发环境通过”和“游戏内通过”；没有游戏内结果时保持待验证状态，不能宣称里程碑已全面完成。

首轮重点：安装加载、已有／缺失条目、反复悬停、UI 开关、模式切换、受限场景恢复、重载后的账号设置、诊断开关。任务阶段增加双栏滚动与变量，效果阶段增加装备或角色状态变化后的数值。

## 9. 关键风险与处理方式

| 风险 | 对应措施 |
| --- | --- |
| 参考词库只有中文或数据来源版本混杂 | 导入时记录并检查覆盖，不把来源混合等同于目标版本已验证 |
| 中英文句数不同、译文重排 | 构建时确认句组关系，缺少对齐时回退段落 |
| 同名术语、别名和普通词歧义 | 保留候选与上下文；不能确定时不注释 |
| 字号变化使左右错行 | 共享句组行高和滚动区域，样式变更触发布局更新 |
| 开关关闭后延迟任务重新写入 | 更新代数和内容身份检查，切换时使旧任务失效 |
| 动态效果缓存导致旧数值 | 缓存包含实际原文／上下文，不只按技能 ID 缓存最终说明 |
| 扩大词库后加载或匹配产生尖峰 | 先建立固定负载，再比较按需加载和索引策略 |
| 开发环境通过但游戏内受限 | 将接口接入与纯逻辑分离，保留明确的游戏内验证状态 |
