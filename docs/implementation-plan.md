日期：2026-11-05；进度更新：2026-11-23。

当前交付：`0.2.0-alpha.1`，13 条手工名称样例、按需数据包、原版物品提示双语卡片、账号设置、界面开关／模式／样式、诊断与可复现 ZIP；P1.5 第一批（提示框刷新不闪烁、中文字体族、Forever 旧全局函数检查、版本号统一、引擎性能指标）已完成，待 Windows 游戏内验证。安装与实际验收见 [Windows 测试指南](windows-testing.md)，代码和具体数据格式见[开发说明](development.md)。

首轮实现采用较少的顶层 Lua 文件组织模块，后续规模增长再拆目录。任务／术语数据结构用合成样例验证，不代表相关游戏界面已实现。正式参考词库尚未导入；当前使用明确标记的手工工程样例，先完成可安装验证链路。

需求依据：[需求与验收约定](requirements.md)。数据设计依据：[数据模型草案](data-design.md)。本文安排实现顺序、模块边界和交付检查；具体文件名与内部接口为初始方案，可在实现中按实际需要调整。

## 1. 交付目标与边界

先交付可供内部测试的 Windows / WoW: Forever 插件，第一条语言路径为英文到简体中文。先以暴雪原版界面跑通流程，再按[第三方插件共存与适配](requirements.md#第三方插件共存与适配)的要求适配主流插件。初始客户端参考为 `1.60.1.70790 / Interface 16001`，实际接口需在开发时核实。

基本功能与性能同时交付。首先跑通物品名称的完整流程，随后增加 NPC 与技能名称、任务双栏阅读、术语注释和动态效果说明。最小版本不以词条数量为成功标准，以数据结构、交互行为和运行成本得到验证为成功标准。

首阶段不实现：本地模型、自由聊天翻译、伴随程序、快捷键、自动场景切换、角色独立配置、多版本词库切换或公开发布自动化。

账号共享设置；开关和模式通过 UI 按钮控制。项目许可证、公开发布安排和具体 Windows 测试环境按用户决定后续讨论，不将这些讨论提前变成开始设计的条件。实际引入第三方内容时仍记录并核对其来源与许可。

## 2. 技术基线与工程组织

### 建议的首版技术选型

以下是开始实现前的技术提案，不代表代码或客户端验证已经完成。先明确运行环境和数据流，再以小样例验证，随后扩展模块。

| 层次 | 首版建议 | 选择理由与边界 |
| --- | --- | --- |
| 游戏内逻辑 | Lua，使用目标客户端支持的语法与 API | 与插件运行环境一致；查询、翻译处理与界面适配分离。具体兼容语法和测试解释器在 P0 核实 |
| 游戏内界面 | 原生 Frame / FontString，由 Lua 创建控件 | 先支持原版 UI 和共享滚动容器；暂不引入第三方 UI 框架，XML 模板有实际需要时再采用 |
| 开发工具 | Python 3，初期优先标准库 | 用于提取、校验、索引生成和打包；仅开发者需要，玩家安装包不依赖 Python |
| 可维护源数据 | UTF-8 JSON，按内容类别及合理大小拆文件 | 便于审阅、多语言编辑和 Git 比较；字段规范与引用校验独立于文件格式 |
| 游戏运行数据 | 构建时生成的 Lua 数据表与预生成索引 | 游戏内直接查询，不在交互时解析 JSON；按功能拆包，验证按需加载后的成本 |
| 用户持久设置 | 账号级 SavedVariables | 保存开关、模式、字体、字号和颜色；与分发词库及临时缓存分离 |
| 临时缓存与诊断 | 有容量限制的内存表 | 不把可重建缓存或逐次诊断记录持续写入账号设置 |

Python 的最低版本与开发依赖在实现工具时记录；Lua 兼容性以实际游戏客户端为准，不直接假定开发机解释器与游戏完全一致。首版无需数据库服务、SQLite 或外部进程依赖；未来聊天模型单独设计。

### 源数据、运行数据与设置分别存储

这里的“翻译数据库”是逻辑词库，不要求引入数据库引擎。数据流为：

`可审阅 JSON → Python 校验／生成 → Lua 数据包 → 游戏内按类型、ID、语言查询`

JSON 是维护入口，生成的 Lua 文件不手工修改。生成器负责字符串转义、稳定输出顺序、引用检查和索引生成；首批运行表以易检查为优先。JSON 中的实体 ID 与生成后的 Lua 索引键必须有明确转换规则，避免字符串键与数字键不一致导致查不到数据。

源文件拆分不等于游戏内按需加载；后者需要独立的数据插件包及加载入口，具体粒度以首次加载与内存测量调整。普通 Lua 文件的分开存放本身不提供按需加载。

账号设置独立保存，并记录设置格式版本以便补齐默认值或迁移。它与词库的 `schemaVersion`、`dataRevision` 职责不同，也不意味着保留多套历史词库。翻译表和可重建缓存不复制进 SavedVariables。

第一轮采用直观的数据编码与 ID 索引。压缩、复杂索引或其他运行库只有在测量表明有收益时再引入；性能核心首先是运行时做多少工作、何时加载、查找范围和对象分配，而非源文件使用哪种格式。

### 工程目录

拟采用以下结构，按阶段增加文件，不预先创建空模块：

```text
addon/
  WoWFeTranslator/
    WoWFeTranslator.toc
    Core/             初始化、账号设置、模式、待执行任务、缓存
    Data/             数据清单和查询入口
    Translation/      变量展开、术语注释、动态文本处理
    Adapters/         原版界面接入，以及按目标插件拆分的第三方适配器
    UI/               按钮、设置、样式、提示呈现、双栏阅读
    Diagnostics/      可关闭的计时和有限统计
  WoWFeTranslator_Data_*/  按功能拆分的运行数据包，随需要增加
data/
  sources/            可审阅数据、来源清单、对齐与术语标注
tools/                导入、校验、生成与内部打包工具
tests/                核心行为、数据一致性和回归样例
benchmarks/           固定负载与测量结果说明
docs/
```

## 3. 模块职责和调用路径

| 模块 | 输入与输出 | 约束 |
| --- | --- | --- |
| Settings / Mode | 个人偏好与当前模式 → 有效功能集合 | 不用切换模式覆盖个人设置 |
| Adapters | 游戏事件和可见内容 → 类型、ID、原文及上下文 | 集中处理游戏 API，检查数据是否可读 |
| Repository | 类型、ID、语言、字段 → 记录及数据状态 | 名称查询不加载整套任务正文 |
| Translation | 记录、原文与参数 → 名称、双语句组或注释片段 | 不依赖具体 Frame，也不决定颜色和字号 |
| Presenters / Style | 内容及显示配置 → 对应界面 | 管理所属控件、排版、刷新与恢复 |
| Scheduler / Cache | 待更新内容与查询键 → 合并任务和复用结果 | 有容量边界、失效机制和取消机制 |
| Diagnostics | 指定处理区间 → 有限样本及统计 | 默认关闭，不把日志写入每次交互路径 |

初始逻辑调用路径：

`事件 → 有效功能检查 → 获取可读上下文 → 查数据／复用缓存 → 必要的翻译处理 → 显示`

名称、任务对照与术语注释共享查询和样式边界，但不强行使用同一套解析算法。数据缺失、无对齐、参数无法解析和接口受限分别返回状态，不用空字符串混淆所有失败情况。

模式预设控制启用哪些能力；左右对照、名称显示和术语注释属于显示策略。最小版本先提供剧情、精简、竞技三个预设，术语模式在相应能力完成后再显示为可用选项。

### 有效功能计算

有效功能由四层共同决定：总开关、场景模式预设、模块开关和运行时能力（功能是否已实现、客户端接口与目标插件是否可用、界面是否受保护）。设置或运行时能力变化时，集中计算一张有效功能表，例如“任务：双栏对照”“物品：名称”“NPC：关闭”，同时增加更新代数。

各适配器的钩子入口只读取自己对应的一项，不满足就立即返回，不在每次回调中重新组合四层条件。数据包的加载也由这张表决定：精简模式不加载正文包，术语模式只加载术语索引，竞技模式不加载任何新数据。界面根据同一张表区分“用户已关闭”和“因模式或能力限制暂停”。

### 适配器结构

原版界面和第三方插件使用同一套适配器约定，核心层不知道具体的界面来源。每个适配器声明：

| 项目 | 内容 |
| --- | --- |
| 目标 | 原版，或第三方插件名称及已验证版本范围 |
| 覆盖界面 | 提示框、任务日志、任务追踪、对话、单位框体等 |
| 所需模块 | 物品、技能、NPC、任务中的哪些 |
| 安装与检查 | 目标加载后安装钩子；检查预期接口，失败时只停用自己并报告原因 |
| 内容提取 | 从界面取得类型、ID、原文与上下文，交给核心查询 |
| 呈现方式 | 使用共享的呈现器，或针对目标界面的专用呈现器 |

调用路径为：`适配器取得上下文 → 有效功能检查 → 查询／缓存 → 翻译处理 → 呈现器`。第三方适配器在目标插件的 `ADDON_LOADED` 之后安装；目标未安装时不创建控件、不注册钩子。适配器代码先放在主插件中按需安装，代码量或加载成本明显增大后，再评估拆成按需加载的独立插件。

同一界面可能同时被多个插件修改。适配器只处理自己确认的目标；识别不了当前界面归属时不显示译文。第三方插件的接口不属于稳定契约，每个适配器都要有对应的接口替身测试，以及记录目标版本的游戏内验证。

## 4. 数据准备与生成

### 单一当前词库

运行包只包含当前数据集。保存 `schemaVersion`、`dataRevision`、游戏与客户端范围以及来源清单，不实现历史数据路由。Git 保存修改历史。

源数据从开始就分开表达实体、术语、正文及标注：

- 实体按类型和 ID 定位，保留各语言名称。
- 术语拥有稳定内部键，可关联实体，支持没有游戏 ID 的概念。
- 正文按字段和语言保存，附可选的句组对齐、变量和术语引用。
- 个人偏好独立存储，不将用户样式或忽略列表烘焙进公共词库。

### 首批样例

参考此前研究的 WoWeuCN Plus 与 qqytqqyt 插件，选取明确版本的包，记录出处和许可。初始建议规模为十余条物品名称、少量 NPC／技能名称，以及几条覆盖不同情况的任务；数量不是验收门槛。

先建立代表性样例，再扩大词库。样例需要覆盖多词名称、缺译、同名歧义、变量、长短句、不同句数、链接和显示标记。只有中文的记录不能冒充完整双语记录，缺少英文或对齐关系时明确标记并补齐。

导入流程：

`固定来源包 → 提取字段 → 规范化记录 → 保留来源 → 对齐／标注 → 校验 → 生成 Lua 包`

源包只作为数据输入，不执行其任意初始化代码。固定正文的语义对齐与术语确认在构建阶段完成；第一批少量样例可以人工核对，游戏内不做语义推断。尚未确认的候选标注不能直接当成确定结果。

生成工具检查 ID、术语引用、字段类型、占位符、对齐范围、源文指纹和数据包元数据。相同输入应产生一致的输出；运行包不含原始下载包、开发笔记或用户聊天记录。

## 5. 开关与更新生命周期

初始化时读取账号设置和轻量数据清单，根据有效能力加载必需数据并接入支持的界面。不要为所有界面提前创建完整控件或编译全部模板。

切换开关、模式、语言或影响输出的配置时：

1. 更新有效能力和相关失效标识。
2. 让旧的排队任务失效，阻止它们再次写入旧结果。
3. 清理本插件拥有的显示内容，或按安全条件恢复原文。
4. 对仍需显示的支持界面安排一次合并刷新。

可采用更新代数作为旧任务失效标识，避免逐个追踪所有延迟回调。刷新执行前同时检查代数、当前界面内容和有效能力。

竞技模式和总开关关闭时，钩子只保留必要的判断；不查询词库、不匹配术语、不渲染译文。无法立即完成的受保护界面恢复作为单独待办，在允许的时机处理。关闭不承诺立即卸载所有 Lua 数据。

性能诊断可独立启用来测量关闭状态的成本。正常关闭诊断时，不保留逐次采样或持续日志工作。

## 6. 实施阶段

工作分为三条轨道（2026-11-24）：

| 轨道 | 内容 | 时机 |
| --- | --- | --- |
| A 插件主体 | 下表的 P0–P6：显示、设置、适配层，以及客户端数据表中的物品、技能等官方名称 | 进行中 |
| B 服务器文本 | 英文采集、离线流水线、本地模型翻译、按 ID 与文本指纹查询的数据包；完成后恢复任务翻译（P3） | A 轨道 P1.5 第一批完成后开始，第一项是可行性验证 |
| C 聊天翻译 | 可行性调研：游戏内限制、游戏内词典方案、游戏外伴随程序方案 | B 轨道有初步成果后 |

A 轨道的依赖顺序为 P0 → P1 → P1.5 → P2 → P3 → P4 → P5 → P6。P3 任务双栏阅读暂缓（2026-11-24），等 B 轨道提供任务文本后再排期，期间只保留接口（见需求文档“任务文本翻译暂缓”）；P2 中的 NPC 名称同样依赖 B 轨道，物品与技能名称不受影响。每阶段形成可审查的交付，不在基础链路尚未验证时扩大数据量或界面覆盖。

| 阶段 | 交付物 | 完成条件 |
| --- | --- | --- |
| P0 技术基线、数据契约与样例 | 记录 Lua 兼容要求与工具版本，明确 JSON → Lua 构建流程、设置存储及加载边界；字段规范、来源清单、代表性数据、校验及生成入口 | 小样例能生成可查询的 Lua 数据；能同时表达名称、双语正文和术语引用；重复生成一致，错误引用能被发现；客户端相关假设列出验证状态 |
| P1 物品名称最小版本 | 可加载插件、账号设置、UI 开关和模式、名称左右对照、基本样式、可关闭性能统计、内部安装包 | 同一提示不重复显示，切换物品无残留，关闭后停止处理，旧任务失效；取得首次与重复查询的测量结果 |
| P1.5 有效功能与适配层 | 四层有效功能表、物品模块开关、适配器约定与状态报告、按类型拆分的数据包清单；EllesmereUI 提示框适配（含 RegisterSkin、RegisterPlugin） | 只关物品模块不影响其他模块偏好；目标插件未安装时零开销；适配器失败只影响自身并出现在报告中；原版与 EllesmereUI 下名称显示均正确 |
| P2 扩展名称覆盖 | NPC、技能名称适配，模块独立开关 | 三类名称复用查询和显示逻辑；关闭一类不影响另一类；增量数据与处理开销有记录 |
| P3 任务双栏阅读（暂缓） | 任务字段查询、变量展开、句组排版、同步滚动；已选任务与对话类插件的适配 | 左右句组在滚动、不同字号和宽度下保持对齐；原版及已适配插件中的接交操作正常；缺字段和切任务正确处理 |
| P4 术语注释 | 预标注渲染、必要的候选匹配、术语模式入口和注释样式 | 原句保留，短语和边界正确；歧义回退；不破坏链接和变量，不重复注释；性能与词库规模有测量 |
| P5 详细效果 | 物品风味文字、技能和装备效果模板、当前数值映射 | 成功匹配时使用当前值，失败保留原文；精简和竞技模式不进入详细解析路径 |
| P6 内部测试收敛 | 扩充已核对词库、内部 ZIP、使用说明、回归与性能报告 | 在已安排的 Windows 客户端完成核心场景验证，记录已知限制和覆盖范围 |

P0 定义并验证术语数据结构，P4 才接入完整注释界面；不能因 P4 较晚而先设计成仅有中文名称的临时数据库。

P1 中剧情与精简模式的显示可以暂时相同，因为只支持名称，但必须保留独立状态和后续能力边界。未完成的功能不以可用按钮误导测试者。

### P1.5 实施计划

目标版本 `0.2.0-alpha.1`。分为两批：第一批修正提示框行为并改进字体，尽快出 Windows 测试包；第二批在测试反馈的基础上重构。每一步单独提交，提交前 `tools/check.py` 必须通过，并补充对应的接口替身测试。

**第一批：先出测试包**

1. **提示框生命周期与闪烁**（`Tooltips.lua`、`Presenter.lua`、`tests/wow_mock.lua`）
   - 区分新建和刷新：在提示框的 `SetOwner` 后置钩子和 `OnHide` 中完全清除；`OnTooltipCleared` 只让排队任务失效，并重新排队一次检查，不立即隐藏卡片。检查时内容相同就保留，不同或已不是物品就隐藏。
   - 判断是否显示改用 `IsVisible()`，兼容 EUI 把提示框挂到隐藏父框体的做法。
   - 物品 ID 优先使用 `TooltipDataProcessor` 回调提供的 `data.id`，取不到时再解析链接。
   - 接口替身补充：刷新时依次触发 `OnTooltipCleared` 和物品回调但不调用 `SetOwner`、父框体隐藏、`SetOwner` 切换物品。断言刷新期间卡片不隐藏，`repeat_skipped` 生效。
2. **中文字体回落**（`Core.lua`、`Presenter.lua`、`UI.lua`）
   - 支持 `CreateFontFamily` 时，为每种字号建立字体族：拉丁字母使用用户选择的字体，简体中文使用随包字体，其他字母表使用客户端默认。按“字体路径 + 字号”缓存，每个组合只创建一次。
   - 不支持时退回现有的 `SetFont`。
   - 设置中的“自定义字体”改为“英文字体”。中文字体固定使用随包字体，暂不开放自定义。
   - 加载字体前先用隐藏的 FontString 检测路径能否加载，失败时提示并回退。

### B 轨道：服务器文本

目标：用英文客户端自行采集服务器下发的英文文本，在游戏外用本地模型翻译，生成随插件分发的数据包。英文由我们采集、译文由我们生成，数据来源完全自主；MaNGOS 本地化包和以后采集的官方中文只作为可选的替换与校对来源（见[数据模型草案](data-design.md#62-任务与-npc-文本的来源调研)）。

**采集范围与方式**

| 内容 | 方式 | 一个人能否完成 |
| --- | --- | --- |
| 任务标题、正文、目标 | 按任务 ID 列表（客户端 QuestV2 表约 6,600 个）限速查询服务器，内容写入本地任务缓存，离线解析 | 可以（待 B0 验证） |
| NPC 名称与头衔 | 通过生物超链接触发查询，写入生物缓存；NPC ID 列表另找来源或按范围尝试 | 可以（待 B0 验证） |
| 进度与完成对话、NPC 对话、说话与喊叫、书信 | 被动收集：只有实际交互或事件发生时才下发 | 需要长期积累 |

长尾内容的补充：开源模拟器（vmangos、cmangos）的英文数据库只作为构建时的 ID 列表和交叉核对，不把其文本打进数据包（GPL 影响需评估）；主插件以后提供可选的采集功能，玩家遇到未翻译的文本时记录英文原文，由上传或伴随程序交回，优先覆盖玩家实际看到的内容。

**流程**

1. **游戏内采集**（独立插件 `WoWFeTranslator_Collector`，不依赖主插件）：
   - 被动记录接任务、进度页、完成页、NPC 对话、书信、NPC 说话与喊叫、悬停或选中 NPC 时界面上出现的文本，附构建号、客户端语言和角色性别。
   - 保存前把玩家名、职业、种族换回占位符，不记录角色名、服务器名和账号信息。按“类型 + ID + 字段”去重，控制文件大小。
   - 主动批量查询在 B0 验证可行后加入，必须限速。
2. **上传**：退出游戏后提交 `WTF\Account\<账号目录>\SavedVariables\WoWFeTranslator_Collector.lua`；以后可由伴随程序自动完成。
3. **离线流水线**（Python，开发机）：安全解析存档（不执行其中的 Lua）→ 校验格式、构建号与语言 → 隐私复查，多人提交时按差异推断占位符 → 合并为数据源 JSON（正文、片段、变量）→ 分句 → 本地模型翻译，套用客户端数据表中的官方术语表 → 校验占位符与术语 → 生成数据包。每条译文记录来源与状态：官方、已审校、机翻。
4. **游戏内查询**：任务按 ID 查询；对话、喊话、书信等按英文原文规范化后的指纹查询。数据包只包含中文与指纹，不包含英文原文。机翻内容明确标注，并可由用户关闭。
5. **增量翻译**（以后）：伴随程序在两次游戏之间读取采集记录，用本地模型翻译新出现的文本并写回插件的数据文件，下次登录或 `/reload` 后生效。

**阶段**

| 阶段 | 交付 | 完成条件 |
| --- | --- | --- |
| B0 可行性验证 | 最小采集插件：按少量任务 ID 和 NPC ID 限速查询；缓存文件解析原型 | 确认 Forever 允许这类查询、实际限速和缓存文件格式；得出“一个人能完成多大比例”的结论 |
| B1 采集插件 alpha | 被动收集、去隐私、去重；根据 B0 结果加入批量查询 | 在英文客户端连续游玩后，存档中没有个人信息，文本可按 ID 配对 |
| B2 离线流水线 | 存档解析、校验、合并、占位符推断、分句、数据源 JSON | 多份存档可重复合并为一致的结果；错误或篡改的提交被拒绝 |
| B3 翻译与术语表 | 从客户端数据表生成官方术语表；本地模型批量翻译与校验 | 抽样审校通过；占位符和术语校验无错误 |
| B4 运行时查询 | 按 ID 与指纹查询的正文数据包；恢复 P3 任务翻译 | 游戏内任务、对话按来源显示，机翻标注与开关生效 |

### C 轨道：聊天翻译（调研）

- **游戏内限制**：插件不能联网，也不能调用模型，游戏内只能做词典、常用语和缩写级别的翻译。按 Midnight 引擎的说明，副本内插件收到的聊天内容是秘密值，需要在 Forever 上实测。
- **伴随程序方案**：读取游戏的聊天日志文件（`/chatlog`），用本地模型翻译后在游戏外的窗口中显示；不能写回游戏内的聊天框。需要验证 Forever 的聊天日志是否可用、写入延迟有多大，以及副本内的聊天是否也会写入日志。
- **双方都装插件时的结构化沟通**：发送方从预设的常用语（组队、职责、集合、交易等）中选择，通过插件消息只发送短语 ID 和参数，接收方的插件按自己的语言显示。整个过程在游戏内完成，不依赖模型，适合 EU 多语言玩家之间的常用沟通。限制：只有双方都安装时有效；插件消息有频率与长度限制，Midnight 引擎下副本内可能无法发送，需要实测。
- **发送方向**：玩家在伴随程序中输入母语，得到目标语言译文，自行复制粘贴到游戏中发送；不模拟按键、不自动发送。
- 调研结论出来前不实现，也不承诺具体形式。

### P3 的排版方案

在原版任务界面旁提供可关闭的双栏阅读面板。一个滚动区域承载两列；每个对应句组共享一行，行高取两侧文字高度的较大值。鼠标在任一列上滚动都改变同一垂直偏移。

字号、宽度或内容变化时重新布局，普通滚动只改变滚动位置，不重复翻译或测量全部文字。长文控件是否需要复用或可见区渲染由实际测量决定，不在原型阶段预设复杂虚拟列表。

测试应覆盖窗口底部、左右文本长短差异、缺少单侧译文、切换任务和隐藏面板。没有可靠句级对齐的记录采用明确的段落对照，不能伪造一一对应。

### P4 的注释方案

优先读取构建阶段的术语引用。对没有预标注且属于支持范围的文本，使用按需匹配索引，不逐条扫描全词库。以原始文本作为输入，避免对已经注释的输出再次注释。

首次出现才注释和用户忽略列表仍为待确认选项；数据和缓存边界允许扩展，但不把这些交互作为 P1 的前置条件。混排中的独立字体与字号先验证实际控件能力，必要时使用片段布局。

## 7. 性能实现与测量

先采用尽早返回、按需加载、ID 查询和合并更新等简单措施。每项额外优化要有固定负载下的前后对比，并同时验证结果正确。

### 三条路径分别测量

| 路径 | 关注点 |
| --- | --- |
| 按 ID 查询名称 | 首次加载、重复查询、提示框刷新和内存增量 |
| 已标注正文渲染 | 变量展开、句组和注释排版、滚动时是否重复处理 |
| 现场文本匹配 | 模板或术语候选数量、缓存命中、长文本与歧义输入 |

缓存条目有容量边界。查询缓存与显示布局缓存按依赖分别失效，避免改颜色就重新解析数据，也避免技能数值变化后仍显示旧译文。失效因素包括数据修订、语言、原文或动态上下文、模式，以及相关样式／偏好修订。

诊断初期使用有界样本，记录调用次数、累计及平均耗时、最大耗时、缓存命中和内存变化；P95 在报告生成时根据保留样本计算，注明样本窗口，不在每次事件中排序。测量工具本身的开销要单独说明。

区分插件处理耗时、数据加载耗时和整体游戏帧表现。P1 取得第一份可用基线后再设定数值预算，不预先宣称任何毫秒或内存目标已经满足。

### 自有计时与引擎指标

插件本身的耗时以 `debugprofilestop` 自行计时为准，覆盖钩子回调、查询、渲染与数据加载。根据 EllesmereUI 源码中作者的实测说明（`EllesmereUI_Ticker.lua`，本项目尚未验证），引擎把脚本处理函数的耗时计入创建该框体的插件，而不是挂钩子的插件。按此规则，挂在 GameTooltip 等暴雪框体上的钩子耗时不会计入本插件，插件列表中的 CPU 数值可能偏低。

诊断报告同时附上客户端提供的 `C_AddOnProfiler` 指标（接口存在且已启用时），例如近期平均与峰值，作为对照。两者不一致时，以自有计时判断本插件的处理成本，并在报告中保留两组数值。引擎指标只在生成报告时读取，不进入每次交互路径。

### 原版界面与 EllesmereUI 对照测量

每个里程碑在两种环境下各测一轮：只启用本插件的原版界面，以及启用 EllesmereUI 的界面（记录其版本与启用的模块）。两轮使用同一角色、地点、UI 缩放和操作脚本，分别记录本插件的自有计时、`C_AddOnProfiler` 指标、内存和帧率。

对照的目的是确认适配器带来的额外成本，以及 EllesmereUI 的提示框隐藏、跟随鼠标等行为下本插件是否产生多余处理，不用于评判 EllesmereUI 本身的性能。

### 开发环境

围绕容易回归的行为做测试：数据引用和生成一致性、缺译回退、占位符展开、缓存失效、关闭后的旧任务、术语边界和标记保护。测试断言行为，不照抄实现。

通过少量游戏接口替身隔离纯逻辑测试，明确其不能验证实际受保护状态、字体测量和 Frame 生命周期。Lua 语法检查与核心逻辑测试使用与目标客户端相容的环境。

### Windows 游戏内

具体硬件、安装目录和测试协作按用户要求稍后安排。每个里程碑分别标记“开发环境通过”和“游戏内通过”；没有游戏内结果时保持待验证状态，不能宣称里程碑已全面完成。

## 9. 关键风险与处理方式

| 风险 | 对应措施 |
| --- | --- |
| 参考词库只有中文或数据来源版本混杂 | 导入时记录并检查覆盖，不把来源混合等同于目标版本已验证 |
| 中英文句数不同、译文重排 | 构建时确认句组关系，缺少对齐时回退段落 |
| 同名术语、别名和普通词歧义 | 保留候选与上下文；不能确定时不注释 |
| 字号变化使左右错行 | 共享句组行高和滚动区域，样式变更触发布局更新 |
| 开关关闭后延迟任务重新写入 | 更新代数和内容身份检查，切换时使旧任务失效 |
| 动态效果缓存导致旧数值 | 缓存包含实际原文／上下文，不只按技能 ID 缓存最终说明 |
| 扩大词库后加载或匹配产生尖峰 | 先建立固定负载，再比较按需加载和索引策略 |
| 开发环境通过但游戏内受限 | 将接口接入与纯逻辑分离，保留明确的游戏内验证状态 |
| 第三方插件更新导致接口变化 | 适配器记录已验证版本并检查预期接口；失败时只停用该适配器并报告，核心功能不受影响 |
| 多个插件修改同一界面 | 优先使用自有控件；改写他人文本前记录所有权，无法确认界面归属时不显示译文 |
