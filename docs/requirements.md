# WoWFeTranslator 需求与验收约定

状态：需求基线；部分核心功能已有内部测试版，实际完成与验证状态见[开发规划](implementation-plan.md)。

记录日期：2026-11-05。

本文记录当前讨论中已确认的产品方向和实现约束。验收项用于验证这些要求，不代表已完成测试；后续范围变化应同步更新本文。

## 1. 产品目标与使用场景

开发一个独立维护、免费开源的 WoW: Forever 翻译插件。首阶段以 Windows 为开发和游戏内验证平台，支持英文客户端显示简体中文。

翻译的主要价值是帮助玩家享受任务、对话、装备与技能说明中的 RPG 内容。玩家进入 PvP 等竞技场景时，需要快速暂停翻译，不应被迫保留阅读细节或承担其解析成本。

项目使用独立仓库 `HongyouZhou/WoWFeTranslator`，不以维护其他插件的 Fork 为交付方式。当前先供内部人员测试，公开发布方式和项目许可证留待后续讨论。可以研究已有实现；引入第三方代码、词库或字体时仍需保留来源并核对其许可。

用户提供的初始测试客户端信息：

| 字段 | 值 |
| --- | --- |
| 游戏版本 | 1.60.1 |
| 构建号 | 70790 |
| 插件接口版本 | 16001 |

这是一份测试环境快照，不是长期兼容承诺。开发和发布时需重新验证实际客户端与所用接口。

## 2. 基础功能范围

基础阶段逐步覆盖以下内容：

- 任务标题、目标、正文及接交任务的相关文本。
- 物品中文名称、风味文字和可可靠匹配的效果说明。
- 技能中文名称、说明与可可靠匹配的动态数值。
- NPC 中文名称和头衔。
- 完整翻译采用英文在左、中文在右的逐句对照；另提供保留英文、只在特定术语后追加译注的阅读方式。
- 字体、字号、颜色及双语排列、间距等阅读样式。

覆盖范围以明确支持的界面为单位扩展，不承诺首版翻译全部游戏文本。缺失记录、字段缺译、参数无法解析或接口受限时保留原文。

当前仅适配暴雪原版界面，不开展第三方任务窗口、提示框或整合 UI 的兼容适配。客户端本身的接口与受保护状态约束仍必须处理。

### 左右对照显示

用户确认的显示目标：英文原文在左，对应中文在右，尽量逐句对齐，而不是把整段译文追加在原文下方。名称等短文本按对应字段成对显示。

任务正文采用原版任务界面旁可关闭的双栏阅读面板，原版接取、完成等操作保留。左右两列必须同步滚动，在字号、宽度或文本长度不同时仍保持对应句组对齐。

逐句对应是语义对应，不是按屏幕自动换行后的行号对应。英文和中文可能存在一句对多句、多句对一句的情况，不能直接按标点切开再按序号配对。

以下为待验证的实现方案，尚未定稿：

- 在数据准备阶段保存句子或句组的对应关系，游戏内直接读取，避免运行时做语义对齐。
- 每个对应单元左右各占一列，行高取两侧所需高度的较大值；各列可独立设置字体和字号。两列使用一个共同的滚动内容区域和垂直偏移，避免仅同步两个独立滚动条的百分比而导致句组错位。
- 没有可靠句级对应的数据先采用明确的段落级对照，不伪造句子对应关系。
- 双栏面板的尺寸、屏幕边缘处理和外观后续确定；具体控件实现需验证共同滚动和句组对齐要求。

ID 解决记录定位，不自动解决译文来源、字段完整性、版本差异、动态参数和句子对齐。任务本身也有 ID，应按 ID 查询；名称和动态说明需要区分处理复杂度。

### 术语注释显示

面向英语熟练、主要需要理解游戏专有名词的玩家。保留英文原句，仅在命中的术语后追加简短目标语言译注，例如 `Stormwind（暴风城）`，不显示整句译文。该方式与完整翻译的左右对照并存，不替代前述显示目标。

术语注释属于基础离线翻译方向，不依赖未来的本地模型。它可用于后续已支持的任务正文、说明文本等界面，不意味着首个物品名称里程碑立即支持任意文本注释。

术语支持必须从初始数据设计开始考虑：保留各语言名称、别名、实体关联和文本中的术语引用，不能只存 ID 到中文名称或整段译文的单向映射。界面功能可以后续接入，但基础数据模型需要同时支持完整对照和术语注释。详见[数据模型草案](data-design.md)。

以下为建议的匹配和交互规则，具体默认值与范围待实现讨论确认：

- 使用带语言、类别和可选实体 ID 的术语表；有明确 ID 或上下文时优先按其消歧。
- 多词名称优先匹配完整短语，处理词边界和重叠匹配，不能把短词误匹配到其他单词内部。
- 存在歧义的普通词不凭字符串命中就强行注释。无法确定含义时保留原文。
- 基于原始文本处理，避免重复注释；保护超链接载荷、颜色标记、纹理标记和动态参数。
- 考虑每个文本块同一术语只注释首次出现，并允许用户将熟悉术语加入忽略列表。插件不自动推断用户掌握哪些词。
- 注释颜色可配置。句内独立字体和字号是否需要单独布局，留待显示层验证，不预先承诺单个原生文本控件具备该能力。

性能上不能把每段文本对整个术语表逐词扫描，也不能因为译注短就假设开销更低。按需建立匹配索引，复用处理结果；缓存需考虑原文、语言、术语表版本、忽略配置和匹配上下文。

## 3. 使用模式

首版通过 UI 按钮手动切换模式和开关，不实现快捷键。命令入口暂不作为必需功能，具体按钮位置和交互后续确定。

| 模式 | 翻译行为 | 性能目标 |
| --- | --- | --- |
| 剧情模式 | 启用用户选择的任务、名称和详细说明翻译，采用个人阅读样式 | 可见内容更新流畅，合并重复处理 |
| 术语注释模式 | 保留英文原文，仅在命中的专有名词后追加简短译注 | 只对变化的支持文本做术语匹配，不执行整句对齐或详细效果翻译 |
| 精简模式 | 仅显示物品、技能、NPC 的中文名称；暂停任务正文与详细效果翻译 | 避免详细效果模板解析 |
| 竞技模式 | 暂停全部翻译，恢复可安全恢复的原文 | 不执行查询、解析或翻译渲染任务 |

模式只控制已经实现的功能。最小物品名称版本不因提供模式切换而宣称具备任务、NPC 或技能翻译。

术语注释与精简模式的区别：前者帮助阅读完整英文段落，在段落内部解释词语；后者减少显示内容，只提供实体名称。实现时将场景预设与呈现策略分离，避免为每个模式复制一套翻译和界面代码。

所有设置和当前模式先按账号共享，不做角色级设置或多套配置管理；跨账号同步不在范围内。个人配置与当前模式仍分别保存。切换到竞技模式不得清空或改写剧情模式下的字体、颜色、双语设置和模块选择；切回后恢复这些偏好。

进入竞技场、战场等场景的自动切换属于后续扩展，首版不做。未来自动切换需允许手动覆盖，不能单凭“是否处于战斗中”推断玩家场景。

## 4. 开关与状态恢复

提供三类独立控制：

1. 总开关：暂停全部翻译，保留模式和模块偏好。
2. 模块开关：任务、物品、技能、NPC 分别控制，且不影响其他仍需工作的模块。
3. 性能统计开关：独立于翻译开关，默认关闭。

有效功能由总开关、当前模式、模块偏好和运行时能力共同决定。界面应能区分“个人已选择开启”和“当前因模式或能力限制而暂停”，避免把暂停误显示成配置丢失。

### 切换行为

- 大多数切换无需 `/reload`。
- 关闭后停止新增翻译处理，并取消或使待执行的翻译任务失效；旧任务不能在关闭后重新写入译文。
- 恢复插件修改过的可安全恢复文本，移除或刷新插件追加的内容。
- 受保护界面的操作遵循客户端限制。逻辑开关立即生效，不能安全执行的界面恢复延后处理。
- 重新开启时按需加载数据，刷新当前支持的可见界面。
- 保存修改前的文本和样式；恢复前检查该内容是否仍属于本插件的修改，避免覆盖游戏或其他插件后续更新。
- 无法移除的钩子在暂停状态尽早返回，不继续查表、解析或渲染。
- 开关关闭不等于所有已加载数据立刻从内存释放。共享数据根据其他功能的需要保留，释放边界需要在实现和验证中说明。

总开关与竞技模式都能停止翻译，但语义不同：总开关用于整体禁用，竞技模式用于保留偏好后的场景切换。开启总开关时仍遵循所选模式。

## 5. 多语言与架构约束

首条验证路径为英文客户端到简体中文。核心接口和数据格式应允许扩展其他语言，不要求首版提供全部语言包。

明确区分：

- 源语言：游戏客户端当前文本的语言。
- 目标语言：希望显示的译文语言。
- 插件界面语言：设置菜单使用的语言。

职责划分：

| 层 | 职责 |
| --- | --- |
| 游戏接口适配 | 取得 ID 和文本、监听界面更新、处理接口版本及受限状态 |
| 翻译核心 | 记录查询、参数处理、缺失回退、缓存及失效 |
| 语言与数据包 | 译文、源语言匹配模板、目标语言输出模板和语言规则 |
| 显示层 | 向支持的游戏界面呈现译文并恢复原始状态 |
| 样式系统 | 根据内容类别和语言配置字体、字号、颜色、间距与双语排列 |

实现要求：

- 名称和任务优先按 ID 查询，记录游戏及数据版本范围。
- 翻译核心不硬编码“源语言必定英文、目标语言必定中文”的假设；首版可以仅提供英文解析器和简体中文输出。
- 动态数值只在参数对应关系能够可靠建立时显示，不猜测伤害、治疗量或时间等数值；失败时保留原文。
- 显示样式与翻译内容分离。样式变化应尽量复用已得到的翻译结果。
- 语言包可提供默认字体建议，允许用户按内容和语言覆盖。
- 程序版本与数据版本独立记录，避免将同一 ID 误当作跨版本文本完全一致的证据。

首版只维护一套当前词库，不实现历史词库并存、用户选择数据版本或跨版本自动路由。保留轻量的数据格式版本、整包修订标识、目标客户端范围及来源版本记录，用于加载校验、追溯和缓存失效；历史内容通过 Git 管理，不随运行包全部分发。

## 6. 性能是首版验收条件

性能从架构开始考虑，并随功能增加验证。不得仅凭重写代码、增加缓存或改用压缩数据宣称更快。

### 实现约束

- 使用明确的事件和界面适配器，避免全局拦截所有 `SetText`。
- 不做无条件全量扫描或每帧翻译；若必须保留更新回调，只处理已标记的待更新内容。
- 合并同一轮界面更新产生的重复请求。
- 按功能需要加载数据，避免登录时解码全词库、编译全部效果模板。
- 优先 ID 查表，文本模式匹配只用于必要的内容。
- 缓存必须有容量边界和失效规则。动态效果不能仅按技能 ID 缓存整段译文，还需考虑实际原文、语言和影响输出的状态。
- 缺失记录、调试日志和统计数据也必须有容量边界。
- 关闭性能统计时停止计时与统计采集，避免诊断功能常态化增加开销。
- 竞技模式或总开关关闭后，不执行翻译工作；必要的开关判断或待恢复界面清理单独核算。

### 测量场景

| 场景 | 主要观察项 |
| --- | --- |
| 首次使用 | 加载、首次查表、模板准备的耗时与内存增量 |
| 重复悬停 | 缓存命中、重复物品或技能的处理耗时 |
| 密集更新 | 任务列表和追踪栏更新时的重复工作与耗时尖峰 |
| 长时间运行 | 缓存、缺失记录、内存是否持续增长 |
| 关闭或竞技模式 | 保留的回调开销，以及是否仍触发翻译工作 |
| 模式快速切换 | 是否积累待执行任务、错误恢复或重复追加译文 |
| 术语注释 | 长文本、多词和重叠术语、重复文本与词库增长时的匹配成本 |

报告至少包含：调用次数、平均耗时、P95、最大耗时、缓存命中与容量、内存变化。首次执行与缓存命中结果分开统计，并记录客户端版本、硬件、测试步骤和其他插件状态。

性能统计必须能够在翻译暂停时独立启用，以便测量关闭状态的成本。插件计时不是整体游戏帧耗时的替代指标，仍需检查实际交互卡顿。

目前不预设未经验证的毫秒或内存门槛。先取得 Windows 游戏内基线，再制定可重复测试的性能预算。开发环境测试用于比较算法，不能替代游戏内结果。

Windows 测试机配置、安装位置和具体游戏内回归流程按用户决定延后安排，不阻塞当前代码设计讨论；性能作为核心验收条件的要求不变。

## 7. 首个可运行里程碑

先完成物品名称提示翻译，验证完整流程：

`提示框事件 → 物品 ID → 中文记录 → 样式处理 → 名称左右对照／恢复`

包含：

- 首批样例数据参考已有翻译插件，先核对来源和字段，再整理成自己的数据格式；不要求从零手工编写所有译文。实际导入前记录插件名称、具体版本及对应许可。
- 样例词库使用支持多语言名称、实体引用和术语扩展的数据结构；不因术语注释 UI 延后而采用无法承载该功能的临时数据模型。
- 物品提示适配、缺失时原文回退。
- 名称的字体、字号与颜色配置，明确品质色与自定义色的选择关系。
- 账号共享的总开关、物品模块开关，以及剧情、精简、竞技三种手动模式，通过 UI 按钮控制。术语注释在支持文本匹配的后续增量中接入，不阻塞此里程碑。
- 可关闭的性能统计。

### 验收检查

- 已知物品名称提供英文左侧、中文右侧的对照，未知物品保持原文。
- 同一提示框反复刷新或重复悬停，不重复追加译文。
- 更换物品后不残留上一个物品的名称、样式或翻译任务。
- 关闭后不再查询词库或执行翻译；已显示内容按恢复规则处理。
- 关闭后排队中的旧任务不会重新添加译文。
- 剧情／精简切到竞技，再切回，个人配置完整保留。
- 同一账号下角色使用共享设置，不依赖快捷键完成开关和模式切换。
- 只关闭物品模块，不影响未来其他模块的偏好和状态。
- 改字体、字号和颜色不要求重载整个界面，且不无故重复翻译。
- 性能统计默认关闭，开启后可以比较首次、重复、关闭状态的开销。
- 在实际 Windows Forever 客户端验证可用性、受限场景行为与性能。

首个里程碑通过后，再逐步增加任务、NPC、技能、动态效果和术语注释，每类功能都同时验证正确性与性能。术语注释增量需验证完整短语和词边界、歧义回退、重复更新不重复注释、标记与链接完整性，以及关闭后的原文恢复。

任务双栏增量需验证：鼠标位于任一列时滚动同一阅读区域；长短句、不同字号、改变面板宽度后两侧对应句组保持同行；切换任务后不会保留上一任务的内容或失效滚动位置。

## 8. 未来设想：本地模型聊天翻译

在基础翻译功能实现后再开始，不属于首版开发范围。

设想是在 Windows 本地运行小型翻译模型，处理聊天自由文本。未来可能需要独立伴随程序，并与插件共享术语、语言配置和视觉规范。

目前只保留这一产品方向，不实现模型加载、伴随程序或外部通信机制，也不要求首版预建相关抽象。

聊天采集通道、译文显示位置、游戏内实时回传的可行性、模型选型、硬件预算与合规性均未确定。不能将普通 UI 插件的可用性视为外部程序方案已经获准，也不能把实时回写原生聊天框列为已承诺功能。

## 9. 后续需要确定的事项

- 项目代码许可证与公开发布方式：当前内部测试，后续再讨论；第三方内容在实际引入时核对其许可与来源。
- 可复现的数据生成、更新和版本校验流程。
